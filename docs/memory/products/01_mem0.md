# Mem0 深度调研报告（Case13 真实验证）

## 0. README/论文亮点（先看这个）

基于 Mem0 README 与源码，memory 相关主张可归纳为：
- `Memory as a service`：LLM / embedding / vector / graph 可插拔
- `Action lifecycle`：写入不是只追加，支持 `ADD / UPDATE / DELETE`
- `Scoped memory`：`user_id / agent_id / run_id` 隔离
- `Filter + rerank (+optional graph)`：检索可控，不是单路 top-k

本文后续映射：
- 定位与接口对应 `1`
- 抽取/存储/检索机制对应 `2`
- 论文主张与实测对齐对应 `3`

术语先读：
- `docs/memory/memory_terms_compare.md`（本系统对应：最小单位=`memory`，非 MemU 式 `item/type/category`）

## 1. 组件定位与最小调用

Mem0 是长期记忆 SDK，不是端到端助手产品。

最小调用链：
1. `memory = Memory(...)`
2. `memory.add(messages, user_id=...)`
3. `memory.search(query=..., user_id=..., limit=...)`

本次测试脚本：
- `tests/research/memory/run_mem0_rich_demo_real.py`

原始输出：
- `backups/memu/runs/mem0_rich_demo_real_output.txt`

### 1.1 本系统术语与对象模型（Mem0 原生）

- 最小对象名词：`memory`（记忆项）
- 生命周期名词：`event`（`ADD/UPDATE/DELETE`）
- 作用域名词：`user_id/agent_id/run_id`
- 可选结构增强：`metadata`（用于过滤与治理）

说明：Mem0 不是 MemU 的 `item/type/category` 结构；它的核心是“记忆项 + 动作生命周期 + scope”。

### 1.2 围绕模型管理记忆（Mem0）

典型交互节奏：
1. 模型/对话产生新事实后，业务侧调用 `add(...)` 写入长期记忆。
2. 下轮模型推理前，业务侧按当前 query 调 `search(...)` 取回候选记忆。
3. 将命中记忆拼成上下文再喂给模型（Mem0 本身不替你自动注入 prompt）。

关键点：Mem0 是“记忆引擎”，不是“loop 编排器”；写入/检索触发时机由外层 agent 决定。

## 2. 机制（How）

### 2.1 抽取
- `add(..., infer=True)` 会先走 LLM 抽取，再给出 action（ADD/UPDATE/DELETE）。
- 本轮 Case13 实测中，落地事件以 `ADD` 为主。

### 2.2 存储
- 抽取后形成 memory item，按 scope 写入。
- 本轮输出里可见记忆 item 含 `id/memory/hash/metadata`。

### 2.3 检索
- `search` 按 query + scope 返回候选记忆。
- 本轮 Query-1..8 都有返回，说明检索链路可用。

## 3. 测试验证（论文主张 ↔ 实测结果对齐）

### 3.1 目标1：原理可观测性

| 主张 | 可观测信号 | 实测 | 结论 |
|---|---|---|---|
| Action lifecycle | `MEMORIZE RESULT` 中出现 `event` | 出现多个 `event: ADD` | 写入动作链路生效 |
| scope memory | 同一 Case13 在同 scope 可重复检索 | Query-1..8 均有结果 | scope 内检索可用 |
| structured item | 返回项含结构字段 | `id/memory/hash/metadata` 均可见 | 结构化存储生效 |

### 3.2 目标2：Case13 抽取了什么、怎么存

从实测输出可直接看到抽取记忆包括：
- `姓名是李明`
- `刚换到星云科技公司工作，担任产品经理`
- `之前喝冰美式，现在换成拿铁，因为喝完胃不舒服`
- `养了一只布偶猫名叫奶油`
- `最讨厌香菜的味道，闻到会反胃`
- `回家后把钥匙挂在厨房门后的挂钩上`
- `常用的开发工具是Chrome、Slack和VSCode`

存储形态（从输出可见）：
- 每条含 `id/memory/hash`
- `metadata` 本轮基本为 `null`

### 3.3 目标3：抽取/检索效果 + 不足分析

抽取效果：
- Case13 核心事实覆盖度高，关键长期记忆基本都被抽到。

检索效果：
- Query-1..8 都能命中目标相关记忆（例如咖啡/香菜/奶油/钥匙）。
- 但每条 query 返回集合偏大，且 `metadata` 基本为空，导致可控过滤能力没被发挥。

不足原因（本轮可见）：
- 本轮未构造 metadata schema，导致 filter/rerank 优势未充分体现。
- 主要依赖向量语义召回，容易“能召回但不够干净”。

## 5. 最终判断（针对 Case13）

- 原理链路：通了（抽取 -> 存储 -> 检索）。
- 抽取质量：好（关键事实覆盖高）。
- 检索质量：中等偏上（能召回，但纯度与过滤可控性还需增强）。

教学定位：
- 适合讲“结构化长期记忆 SDK”的主流程。
- 也适合讲“metadata 设计对检索纯度的重要性”。
