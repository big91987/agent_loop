## 3. 当前最大问题：EverMemOS passive_write 很慢

### 3.1 现象

用户贴过一次真实运行日志：

```text
[RUNTIME] [PHASE] post_model | model_step=41175ms | t+41180ms
[RUNTIME] [PHASE] turn_persist_start | post_model=1ms | t+41182ms
[RUNTIME] [PHASE] turn_persist | turn_persist_start=35691ms | t+76873ms
```

这说明模型本身用了约 41s，模型结束后又在 `turn_persist_start -> turn_persist` 卡了约 35.7s。

### 3.2 定位结论

EverMemOS worker 日志显示：

```text
role=user      memory_manager_ms=25    total_ms=31    count=0
role=assistant memory_manager_ms=35614 total_ms=35616 count=0
```

结论：

- 慢点不是 session markdown 保存。
- 慢点不是 v7 runtime phase。
- 慢点在 EverMemOS 的 `memory_manager.memorize(req)`。
- 特别慢的是 assistant 侧被动写入。
- 即使最终 `count=0`，EverMemOS 仍然可能花几十秒做边界检测/抽取判断。

### 3.3 代码链路

v7 结束模型后同步调用：

```text
loops/agent_loop_v7.py
  -> self.memory_runtime.passive_write(...)
core/memory_v6_3.py
  -> EverMemOSAdapter.passive_write(...)
  -> _memorize_message(role="user")
  -> _memorize_message(role="assistant")
memory_systems/v6_3_evermemos/evermemos_worker.py
  -> STATE["memory_manager"].memorize(req)
/Users/admin/work/EverMemOS/src/biz_layer/mem_memorize.py
  -> memory_manager.extract_memcell(...)
/Users/admin/work/EverMemOS/src/memory_layer/memcell_extractor/conv_memcell_extractor.py
  -> llm_provider.generate(prompt)
```

当前 adapter 会把一轮 turn 拆成 user 和 assistant 两次 EverMemOS `memorize`。第一条 user 没历史时通常很快；第二条 assistant 有 user 历史，触发 LLM 边界检测，因此慢。

### 3.4 旧 400 问题

之前出现过：

```text
HTTP Error 400: invalid params, binding: expr_path=response_format.type, cause=missing required parameter (2013)
```

根因在 `/Users/admin/work/EverMemOS/src/memory_layer/llm/openai_provider.py`：旧实现无条件发送 `response_format: None`，MiniMax 兼容接口将其判为参数错误。

当前 EverMemOS 本地代码已经修成只在 `response_format is not None` 时发送字段。旧 400 在 worker log 里只看到旧记录，最新慢日志没有 400。

但 EverMemOS 内部仍有多层 5 次 retry：

- provider: `max_retries = 5`
- boundary detection: `for i in range(5)`
- event_log / foresight extractor: 也有 `range(5)`

所以如果未来再有参数错误或 JSON 解析错误，会再次放大延迟。

### 3.5 建议修法

短期优先：

1. v7 默认不要同步写 assistant 到 EverMemOS。
2. `turn_persist` 只做本地 session 快速保存。
3. EverMemOS passive write 改成后台 job。
4. 对 assistant_text 加 gate：低价值回复、帮助菜单、寒暄、工具列表说明直接 skip。
5. worker 里增加更细 stage timing：`extract_memcell`、`extract_episodes`、`extract_foresights`、`extract_event_logs`、`process_memories`。

中期：

1. 引入 Hermes 风格 `MemoryProvider` lifecycle：
   - `prefetch`
   - `sync_turn`
   - `queue_prefetch`
   - `on_pre_compact`
   - `on_delegation`
   - `on_memory_write`
2. v7 内部不要让外部 memory backend 阻塞主回答。

## 4. Context / Compact 研究结论

我们对比了 Codex CLI、Claude Code、Hermes 和当前 OpenClaw/v7。

### 4.1 Codex CLI

参考仓库：`openai/codex`。

优点：

- `core / exec / tui / protocol / thread-store` 分层清晰。
- sandbox / approval 是一等公民。
- compact 更像 replacement history，而不是普通追加 summary。
- 适合作为 v7 Runtime Kernel 的架构参考。

可借鉴：

- driver/kernel 分层。
- protocol/event/thread-store。
- sandbox approval policy。
- compact 后重写 active history。

### 4.2 Claude Code

本地路径：

```text
/Users/admin/work/claude-code-main
```

关键实现：

- `src/services/compact/compact.ts`
- `src/services/compact/autoCompact.ts`
- `src/services/compact/microCompact.ts`
- `src/services/compact/sessionMemoryCompact.ts`
- `src/utils/messages.ts`
- `src/utils/sessionStorage.ts`

Claude Code 的 context 管理是三层：

1. microcompact：先清理/压缩旧 tool result。
2. session memory compact：优先复用后台 session memory summary。
3. full compact：生成 summary、写 compact boundary、恢复文件/plan/skill/tool/MCP 上下文。

特别值得借鉴：

- `compact_boundary`
- `preservedSegment`
- resume 时真的 prune transcript
- post-compact restore
- `PreCompact` / `PostCompact` hook
- tool output 先裁剪，不要直接总结全部工具输出

### 4.3 Hermes

本地路径：

```text
/Users/admin/work/hermes-agent
```

关键实现：

- `run_agent.py`
- `agent/memory_manager.py`
- `agent/memory_provider.py`
- `tools/memory_tool.py`
- `tools/skill_manager_tool.py`
- `tools/skills_tool.py`

Hermes 的沉淀机制：

| 类型 | 是否后台 agent | 触发/执行 |
|---|---:|---|
| built-in memory 主动保存 | 否 | 主 agent 直接调 `memory` |
| built-in memory 后台 review | 是 | turn 结束后后台 `review_agent` 调 `memory` |
| skill 主动沉淀 | 否 | 主 agent 直接调 `skill_manage` |
| skill 后台 review | 是 | turn 结束后后台 `review_agent` 调 `skills_list/skill_view/skill_manage` |
| external memory provider | 否 | lifecycle hook：`prefetch/sync/queue/on_delegation/on_memory_write` |

Hermes 最值得借鉴的是：

- memory provider lifecycle。
- skill 后台 review agent。
- memory/skill tool 分离。
- 不把 memory backend 固死在主 loop 里。

### 4.4 四者对比

| 系统 | 优点 | 缺点 | 对 v7 的价值 |
|---|---|---|---|
| OpenClaw/v7 | 可控、Python 易实验、phase/event 已成型 | ContextManager/MemoryProvider/compact boundary 还不完整 | 我们自己的实验内核 |
| Hermes | memory provider 和 skill review 成熟，多平台工具体系强 | 主 loop 大而杂，feature/config 很多 | memory/skill 沉淀机制 |
| Claude Code | 长会话 context 生存能力最强 | 复杂度高，产品补丁多 | microcompact、boundary、resume pruning |
| Codex CLI | 架构最清晰，kernel/driver/protocol 分层好 | memory/skill 不是重点 | Runtime Kernel、sandbox、protocol |

建议组合路线：

- Runtime Kernel 学 Codex。
- Context & Compact 学 Claude Code。
- MemoryProvider / Skill review 学 Hermes。
- OpenClaw/v7 保持 Python 可实验性和清晰文档。

## 7. 下一步建议

### P0：修 v7 体感慢

1. 在 v7 增加 `MemoryWriteQueue` 或最小后台线程，把 EverMemOS passive write 移出同步 turn。
2. `turn_persist` 只保存 session 和 enqueue memory job。
3. 默认 skip assistant passive write，或者通过配置控制：

```json
{
  "memory_backend_config": {
    "passive_write_assistant": false,
    "passive_write_async": true
  }
}
```

4. worker 日志补 stage timing。

### P1：ContextManager

1. 引入正式 `ContextManager`。
2. 区分：
   - full transcript
   - active context
   - compact summary
   - memory context
   - tool outputs
3. 先做 tool output microcompact。
4. 再做 compact boundary / checkpoint。
5. resume 时只加载 boundary 后的 active chain。

### P2：MemoryProvider 抽象

从 Hermes 借 lifecycle，但保持 v7 简洁：

```python
class MemoryProvider:
    def initialize(...)
    def prefetch(query, session_id): ...
    def sync_turn(user, assistant, session_id): ...
    def queue_prefetch(query, session_id): ...
    def on_pre_compact(messages): ...
    def on_delegation(task, result): ...
    def shutdown(): ...
```

### P3：Skill 后台 review

不要一上来频繁自动改 skill。建议先做只读建议模式：

1. turn 后后台 review。
2. 先输出 candidate。
3. 需要显式确认后再写 `SKILL.md`。
4. 后续再开放自动 patch。

## 9. 当前最重要的工程判断

短期不要继续把复杂 memory backend 同步塞在主 turn 末尾。`passive_write` 应该从“用户等待路径”变成“后台沉淀路径”。

v7 的目标也不应该只是“能跑更多 memory backend”，而是把 agent loop 收敛成：

```text
RuntimeKernel
  -> ContextManager
  -> ToolRuntime
  -> MemoryProviderRuntime
  -> SessionStore
  -> Trace/Event Protocol
```

这份文档之后的第一刀，建议直接落在：

```text
v7 async memory persist + assistant passive write gate
```

它能最快改善体感，也能逼出 MemoryProviderRuntime 的边界。
